# ADR 0004: Vault key, recovery, and portable backup lifecycle

Status: Proposed; implementation and qualified independent security approval
are required before this decision may be marked Accepted.

Date: 2026-09-02

Audience: security, client, storage, backup, migration, and QA owners.

Owners: Security Architecture and Client Platform.

Requirements: `REC-001` through `REC-007`, `BAK-001` through `BAK-006`,
`SEC-KEY-001` through `SEC-KEY-006`, and `MIG-001`.

## Context

The preview derives a record-encryption root directly from the Master Password
in some product paths. Its disabled password-change prototype re-encrypts
records and can leave salt metadata and ciphertext in different states. The
existing recovery-looking value is not a supported way to unwrap the key that
encrypted an existing Vault. Existing backup wire components and independent
oracle vectors do not yet form a reviewed portable recovery ceremony.

The PRD instead requires one random Vault Key. The Master Password and Recovery
Key must independently wrap that same Vault Key. Password change may replace
only the password wrapper. A full Vault Key rotation is a separate,
generation-aware transaction. A portable encrypted backup must carry enough
versioned, authenticated metadata to restore a non-empty Vault in a clean
environment.

This ADR defines that target. It does not claim that the target is implemented,
audited, or approved. Product controls remain unavailable until the required
implementation and evidence exist.

## Decision

### Terminology and ownership

- **Vault Key** is a 32-byte secret generated by the operating-system CSPRNG.
  It is never derived from a password or Recovery Key. Existing kernel symbols
  named `root_key` refer to this value and are a code-level legacy alias only.
- **Password KEK** is derived from the exact UTF-8 Master Password and a fresh
  16-byte salt using the versioned Argon2id profile. A domain-separated
  HKDF-SHA-256 expansion turns the Argon2id output into the password wrapping
  key.
- **Recovery Key** is 32 bytes generated by the operating-system CSPRNG. Its
  human representation is the checksummed Base32 form already covered by the
  `recovery-human-form` vector. A domain-separated HKDF-SHA-256 expansion turns
  the decoded bytes into the recovery wrapping key.
- **Backup Key** and **backup authentication key** are separate
  domain-separated HKDF-SHA-256 outputs derived from the Vault Key and the
  immutable backup identity.
- Password wrappers, recovery wrappers, key-confirmation records, and portable
  backups are client-created cryptographic objects. Ciphertext-only services
  may store and compare opaque bytes and revisions but must not receive their
  plaintext keys.

The machine-readable authority for sizes, domains, required context, and state
transitions is
[`key-lifecycle-v1.json`](../../contracts/protocol/key-lifecycle-v1.json).
The binary grammar is
[`key-lifecycle-v1.cddl`](../../contracts/cddl/key-lifecycle-v1.cddl).

### Key hierarchy

```text
Master Password --Argon2id--> password material --HKDF(password domain)--+
                                                                         |
Recovery Key -----------------------------HKDF(recovery domain)----------+-- authenticated unwrap --> Vault Key
                                                                         |
Vault Key --HKDF(item domain)--> item keys                               |
          --HKDF(confirm domain)--> key-confirmation key                  |
          --HKDF(backup domain)--> backup encryption/authentication keys  |
```

The two wrappers encrypt the same 32-byte Vault Key. Their AEAD domains,
nonces, KDF inputs, and authenticated contexts are distinct. Wrapper context
binds protocol version, suite, immutable source deployment scope, Vault ID,
key generation, wrapper purpose, and the wrapper-specific identifier and
parameters. Copying a wrapper to another Vault, generation, suite, or purpose
must fail authentication.

The V1 password profile is Argon2id version `0x13`, 65,536 KiB, three
iterations, one lane, a 16-byte random salt, and a 32-byte output. The one-lane
choice preserves the current portable implementation profile; it is explicitly
part of the pending security review and is not justified by the presence of a
test vector alone. Unknown profiles or out-of-policy parameter values fail
closed. Password bytes are exact UTF-8 and are not trimmed, normalized, or
case-folded.

HKDF uses SHA-256. V1 retains the kernel's existing all-zero 32-byte extract
salt and binds an ASCII domain plus deterministic-CBOR context in `info`.
Whether V2 should use a nonzero protocol salt is a future protocol-version
decision, not a runtime setting.

Password and recovery wrapper encryption uses XChaCha20-Poly1305 with a fresh
24-byte CSPRNG nonce, a 32-byte key, and a 16-byte tag. Nonces are never copied
between wrapper attempts. The ciphertext plaintext is exactly the 32-byte
Vault Key. Failure to authenticate is a terminal error for that attempt and
must not mutate metadata.

### Key confirmation

Every Vault has exactly one active key-confirmation record per active Vault Key
generation. Its storage identity is scoped by principal and Vault, even when a
fixed internal logical name is used. It is not discovered by scanning ordinary
items.

After a password or recovery wrapper opens, the client derives the
key-confirmation key from the candidate Vault Key and decrypts the confirmation
record. The expected plaintext commits the protocol, suite, source deployment
scope, Vault ID, and key generation. The client compares it in constant time.
Missing, duplicate, corrupt, future-version, or mismatched confirmation data is
a repair-safe failure, not an empty Vault and not an invitation to create new
metadata.

### Master Password change

Password change uses one compare-and-set transaction over the versioned Vault
metadata row:

1. Read one metadata revision and verify the current password wrapper.
2. Confirm the resulting Vault Key using the active key-confirmation record.
3. Generate a new salt and nonce, derive the new Password KEK, and wrap the
   unchanged Vault Key.
4. Open the candidate wrapper with the new password and confirm the same Vault
   Key before any persistent write.
5. Atomically compare the metadata revision and replace only the password
   wrapper, its profile, and wrapper revision. Item ciphertext, the recovery
   wrapper, key generation, and confirmation record do not change.
6. Read back and verify the committed wrapper before reporting success.

A failure before the metadata commit leaves the old bytes untouched. A failure
after a successful commit may produce an uncertain client response, but retry
must read the authoritative revision and deterministically establish whether
the old or new wrapper committed. Best-effort reverse item writes are forbidden.

### Recovery and Recovery Key regeneration

Clean-state recovery requires a Vault source containing the versioned recovery
wrapper and key-confirmation record, plus the user's Recovery Key. The process
must work without the old Master Password or prior application state:

1. Parse and authenticate all wrapper and Vault metadata before mutation.
2. Decode the Recovery Key, derive the recovery wrapping key, and unwrap the
   existing Vault Key.
3. Validate the key-confirmation record and the complete source manifest.
4. Require a new compliant Master Password and create a candidate password
   wrapper around that same Vault Key.
5. Restore into empty staging, compare the canonical fixture manifest, and
   atomically attach or commit the staged Vault only after every check passes.
6. Verify the new password, retained Recovery Key, item data, tombstones, and
   post-recovery CRUD before reporting success.

Wrong, altered, truncated, obsolete, or other-Vault Recovery Keys must fail
without destination mutation. The old password wrapper must not be retained as
an alternate active wrapper after recovery.

Recovery Key regeneration is a separate re-authenticated transaction. It
requires a verified portable encrypted backup, creates new recovery material,
recovery ID, nonce, and wrapper around the unchanged Vault Key, verifies the
candidate, and atomically replaces the old recovery wrapper. A successful
replacement invalidates the old Recovery Key. A failed replacement leaves the
old Recovery Key usable.

### Vault Key rotation

Vault Key rotation never shares the password-change code path. Rotation first
creates and verifies a portable encrypted backup. It then creates a new random
Vault Key and generation, stages every re-encrypted item and tombstone with
durable progress, builds new password/recovery wrappers and confirmation data,
and validates a complete successor manifest. One final atomic generation
pointer switch makes the successor active. Resume is idempotent; rollback
discards incomplete successor state and never reconstructs the prior Vault by
best-effort reverse writes.

The detailed staged rotation remains an implementation task in sequence 5.
The existing `root-rotation` vector is provisional design evidence, not proof
that the storage transaction or recovery behavior exists.

### Portable encrypted backup

The portable container is a deterministic-CBOR object described by the CDDL.
Its authenticated header includes:

- protocol, suite, and backup format versions;
- immutable source deployment scope, Vault ID, backup ID, creation time, and
  Vault Key generation;
- exact password and recovery wrappers needed to access the same Vault Key;
- the key-confirmation envelope;
- manifest and account-state revision/hash bindings;
- item and tombstone counts, compatibility bounds, and chunking parameters;
- the encrypted payload and an outer authentication tag.

The backup encryption key and outer authentication key are separately derived
from the Vault Key with the Vault ID, backup ID, key generation, and format
version in their contexts. The payload retains the existing V1
`crypto_secretstream_xchacha20poly1305` framing: fixed-size data frames use
`TAG_MESSAGE`, exactly one authenticated final frame uses `TAG_FINAL`, and
trailing bytes are rejected. The final encrypted frame commits the header
digest, chunk count, logical size, padded byte count, and logical snapshot
digest.

Backup creation must write a new file in the destination directory, flush file
content and required directory metadata, close it, reopen and fully verify it,
and only then atomically rename it over the chosen destination. A failure
deletes only the new temporary file and never replaces a previously verified
backup.

Restore parses bounded lengths, verifies the outer authentication, streams and
final tag, complete logical snapshot digest, versions, wrappers, confirmation,
and manifest before destination mutation. Records are restored into an empty
staging target. Attach/rename/transaction commit occurs only after all checks
pass. Unsupported future versions, tamper, truncation, trailing data, wrong
Vault, wrong key material, duplicate identities, or non-empty-destination
policy mismatch fail without mutation.

### Versioning and migration

Protocol version, suite ID, wrapper version, key-confirmation version, backup
format version, and persisted metadata schema version are independent explicit
integers. Readers reject unknown mandatory fields and unsupported future
versions. Writers emit only their declared current version. A format change
that alters authenticated bytes, key derivation, parsing, or transaction
semantics requires a new protocol or format version and compatibility entry.

Migration follows parse, verify, back up, stage, verify, commit. Before changing
persisted cryptographic metadata, the client must create and verify a portable
pre-migration backup. A failure leaves either the complete old state or the
complete new state unlockable; mixed wrappers, generations, or schemas are
forbidden. A binary may roll back only when the compatibility contract says it
can read the committed data version.

## Rejected alternatives

- Deriving the Vault Key directly from the Master Password: password change
  would require item re-encryption and recovery could not independently unwrap
  the existing key.
- Re-encrypting all items for Master Password change: it expands the atomic
  transaction and can strand mixed ciphertext and metadata.
- Treating a syntax-valid Recovery Key as proof of recovery: checksums detect
  transcription errors, not ownership of the Vault Key.
- Storing one global verifier identity or filtering all Vaults on the client:
  neither enforces principal/Vault isolation at storage and authorization.
- A server snapshot without wrappers, confirmation, authenticated versioning,
  and a destructive clean-target drill: it is operational data movement, not a
  portable encrypted backup.
- Best-effort rollback after a partially committed rotation: it cannot prove
  reconstruction of the prior state.

## Evidence and approval gate

The repository currently contains independent-reference-oracle vectors for
`recovery-human-form`, `unlock-wrap-buckets`, `native-web-bootstrap`, and
`root-rotation`, plus standalone C/libsodium backup fixtures for empty,
one-byte, exact-chunk, and multi-chunk payloads. The lifecycle checker validates
their canonical hashes, generator-source hashes, and binary sidecar hashes.

Those vector rows explicitly say `ai-non-human-reviewed`; the approved reviewer
registry is empty; and the upstream fixed-decrypt backup fixture remains
blocked. Therefore they do not satisfy qualified independent review. Before
this ADR may become Accepted and sequence 4 may become Complete, the owner must:

1. appoint an independent cryptography reviewer through the owner-authenticated
   registry process;
2. obtain signed review records for this ADR/contract and every relied-on vector
   family, including the backup corpus and blocked upstream capture disposition;
3. resolve every review finding and update the threat model and compatibility
   contract;
4. change the machine-readable lifecycle review state only after the checker
   verifies the registered reviewer, subject hashes, scope, and signatures; and
5. record Security and QA approval without describing automated or AI review as
   independent human approval.

Implementation of sequence 5 must not begin as a supported product flow before
this gate. Experimental implementation work may proceed only with inert test
data, explicit feature status, and no recovery or production-readiness claim.
